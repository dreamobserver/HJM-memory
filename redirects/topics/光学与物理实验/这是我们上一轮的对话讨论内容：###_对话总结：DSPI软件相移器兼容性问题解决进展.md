3.  **堆栈分析验证**：
    -   即使找到了上述跳转，也按照原计划，让程序继续运行直到触发 `MessageBoxA`。

        -   通过交叉引用，你可以找到**所有**潜在的检测点，避免只修补一处，点击另一个按钮又报错的情况。

3.  **制定修补方案**：

### 现象分析与修正策略

#### 为什么会出现“命中75次”但“相移器检测时命中0次”？

1.  **启动期的COM口调用**：软件在启动时可能会枚举系统所有硬件设备、查询可用串口、或与其他硬件（如加密狗、打印机、其他仪器板卡）通信。这些操作底层都可能调用 `CreateFileA` 来尝试打开各种设备接口（包括 `COM1`, `LPT1`, `USB` 等虚拟端口）。这解释了那**75次无关的命中**。
2.  **真正的检测时机**：相移器的检测逻辑，正如你发现的，是**延迟加载**或**按需加载**的。它只有在用户执行特定功能（如点击“采集”）时，软件才会去尝试打开**特定的、在配置文件中预设好的那个COM口**（比如 `COM5`）。你之前设置的 `strstr(rcx, "COM")` 条件断点过于宽泛，无法过滤出这一次特定的调用。

#### 新的、更精确的调试方法

我们需要一个能**精准过滤**出那次特定调用的方法。

**方法一：精确条件断点（首选）**

既然我们知道软件配置中预设了相移器的COM口（比如从配置文件或注册表读出的 `COM5`），我们可以设置一个精确得多的条件断点。

1.  在 `CreateFileA` 开头设置条件断点。
2.  条件不再是模糊的 `"COM"`，而是具体的端口名，例如：
    ```
    strcmp(utf8(rcx), "COM5") == 0
    ```
    *   `rcx` 是 `CreateFileA` 的第一个参数，即指向设备名字符串的指针。
    *   `strcmp()` 比较两个字符串是否完全相等。
    *   `== 0` 表示相等时断下。

**如何获知具体的COM口号？**
-   查看软件的 `.ini` 配置文件、注册表设置、或安装目录下的其他文本文件。
-   如果找不到，**方法二**可以帮你找到它。

**方法二：内存断点（数据访问断点）- 强力技巧**

如果不知道具体的COM口号，我们可以让软件“告诉”我们。

1.  **让程序完全启动**。
2.  **在调用堆栈中找到线索**：采用你上次的成功经验。
    -   在 `user32.MessageBoxA` 上设断点。
    -   点击“采集”，触发断点。
    -   在调用堆栈（Alt+K）中，找到最靠近你自己程序模块（通常是地址最高的那个）的返回地址。
    -   **向上滚动**，查看这个函数的反汇编代码。在调用 `OpenPort`/`CreateFileA` 之前，必然有一条指令是准备参数（即把 `COMx` 字符串的地址移动到寄存器中）。这个字符串很可能是从一个全局变量或者栈变量中加载的。
3.  **定位数据**：找到那条指令，例如 `mov rcx, qword ptr [some_address]`。这个 `some_address` 就是存储着 `COM5` 字符串的内存地址。
4.  **设置内存断点**：
    -   在转储窗口（Dump）中，跳转到 `some_address`。
    -   你会看到那里的数据是 `C O M 5 ...` （十六进制形式 `43 4F 4D 35 00`）。
    -   右键该地址 -> **Breakpoint -> Hardware, on access -> Word**。
    -   这个断点的意思是：**当任何指令要读取这个地址处的数据时，中断**。这意味着下次软件准备打开COM口时，只要它来读取这个字符串，调试器就会立刻断下，从而让我们在调用 `CreateFileA` **之前**就抓住它。

**方法三：日志法**

如果断点不好用，可以写一个简单的脚本，记录下所有 `CreateFileA` 的调用参数，然后事后分析。
在 `CreateFileA` 的条件断点里使用这个命令：
